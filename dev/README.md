# Developing the OpenVidu Agent Plugin

*This is the development documentation. The page for the people who **use** the
plugin is [`../README.md`](../README.md).*

The repository **is** the plugin: an [Agent Plugins 1.0](https://agent-plugins.org)
package that bundles the OpenVidu documentation MCP server
(`https://docs-mcp.openvidu.io/mcp`) with the skills that teach an agent how to
use it, so users get both in one install instead of pasting a URL into a config
file and copying skill directories by hand.

The root of the repository is the root of the package, and that is not
cosmetic: every client installs an Agent Plugin from a location whose root is
the plugin — VS Code's "Install Plugin From Source" takes a repository URL,
Kiro and Cursor import a repository, Claude Code fetches the GitHub source
named in the marketplace entry.

**That is why this directory exists.** Everything needed to build and validate
the package, and this documentation, lives under `dev/` so the root shows the
package and nothing else. It buys legibility, not bytes: neither Agent Plugins
1.0 nor Claude Code has a mechanism for excluding files from a plugin, so
`dev/` is cloned onto every user's machine along with the rest. One directory
to mentally skip is better than four. No client reads it, and none rejects
extra files.

The MCP server itself lives in a different repository
([OpenVidu/openvidu-docs-mcp](https://github.com/OpenVidu/openvidu-docs-mcp)),
which is where the documentation index, the tools and the deployment are
maintained. This repository only carries what a client installs.

## What is in it, and what is generated

```text
plugin.json                      ← source of truth: identity and version
mcp.json                         ← source of truth: the endpoint
skills/openvidu-version-edition-product/SKILL.md
README.md                        ← the page users land on
docs/manual-setup.md             ← the same components, configured by hand
.claude-plugin/plugin.json       ┐
.claude-plugin/marketplace.json  │ generated by dev/build_plugin.py
.mcp.json                        ┘
AGENTS.md                        ← the invariants, for a coding agent
CLAUDE.md                        ← three lines, pointing at AGENTS.md
dev/README.md                    ← this file
dev/build_plugin.py              validate + generate
dev/schemas/                     vendored Agent Plugins 1.0.0 schemas
dev/tests/test_plugin.py         the only feedback loop before publishing
dev/marketplace-submission.md    one-off: getting listed by Anthropic
dev/requirements.txt             pytest + jsonschema, nothing shipped
dev/pytest.ini                   testpaths + the import path for the tests
```

**Run every command in this document from `dev/`.** Nothing in the tooling
looks at the working directory — `build_plugin.py` resolves the package from
its own location — but `pytest` does: it finds `pytest.ini` by walking up from
its arguments, so from the repository root there is no configuration and the
tests fail to import `build_plugin`. One directory to be in, and the whole
toolchain works.

```bash
cd dev
pip install -r requirements.txt
python build_plugin.py           # validate + regenerate
python build_plugin.py --check   # fail if stale (the test suite runs this)
pytest
```

**Why there are two sets of files.** Claude Code does not implement Agent
Plugins: it reads `.claude-plugin/plugin.json`, `.mcp.json`, and spells the
Streamable HTTP transport `http` instead of `streamable-http`. Generating its
files from the portable pair keeps the endpoint and the version in one place;
`--check` in the tests is what stops someone hand-editing a copy.

**A deliberate deviation.** Specification §8 says client-specific files belong
under a reverse-domain directory (`com.anthropic.claude-code/`). Claude Code
only looks at the plugin root, so the generated files sit at the root. No
Agent Plugins client rejects extra files, and the portable trio is untouched,
so conformance for every other client is unaffected. Revisit this if Claude
Code adopts the standard — the whole `.claude-plugin/` branch then disappears.

## Names, and why they are what they are

| Thing | Value | Reason |
|---|---|---|
| Plugin | `openvidu` | The repository will grow more skills than the documentation ones, so the package is named after the product, not the feature. It is also the skill namespace in Claude Code (`/openvidu:…`) |
| Marketplace | `openvidu` | Public-facing: users type `/plugin install openvidu@openvidu` |
| MCP server | `openvidu-docs` | Tools appear under this name in the client |
| Skill | `openvidu-version-edition-product` | Must match its directory name; self-describing in clients that don't namespace skills. Named after the three facts it pins: version, edition, product |

## Versions

`plugin.json`'s `version` is this repository's only version number, and it
tracks *the package*: bump it when anything here changes. It is deliberately
unrelated to the two numbers in `openvidu-docs-mcp` — the server package
version and the OpenVidu documentation versions the server indexes.

Clients use the plugin `version` to decide whether an update is available, so
a change published without a bump reaches nobody. SemVer: major if an existing
install would behave differently (the endpoint moves, a skill's contract
changes), minor for a new skill or tool, patch for wording.

## Publishing

A push to this repository *is* the publish. The release procedure is therefore

1. Edit `plugin.json`, `mcp.json`, `skills/` or `README.md`.
2. Bump `version` in `plugin.json`.
3. `python build_plugin.py` to regenerate the Claude Code files.
4. `pytest` — a package is only ever exercised by someone else's client, so
   the suite is the last check before it reaches one.
5. Commit and push.

`README.md` is what users see on GitHub and the closest thing to a product
page for the plugin; `docs/manual-setup.md` carries the by-hand route for
clients that don't load Agent Plugins yet, which is kept out of the README on
purpose — it is long, per-client, and irrelevant to most readers. Keep both in
step with `mcp.json`: a test asserts the endpoint they quote is the one the
package actually ships.

### Before the first publish

- [ ] `https://docs-mcp.openvidu.io/mcp` answers. A plugin that installs
      cleanly and then fails to connect is worse than no plugin.
- [ ] Decide the license. `plugin.json` deliberately has no `license` field;
      add it, plus a `LICENSE` file, once that is settled.
- [ ] Bump `version` to `1.0.0`.
- [ ] `claude plugin validate ..` passes — the package is the parent
      directory (needs the Claude Code CLI, so it is not part of `pytest`).
- [ ] The marketplace listing, if you want one:
      [`marketplace-submission.md`](marketplace-submission.md).
- [ ] Install it from this repository in at least Claude Code and one Agent
      Plugins client, and confirm a search returns real documentation.

## Adding a skill

Create `skills/<name>/SKILL.md` — at the repository root, not under `dev/`:
it is part of the package. Give it frontmatter whose `name` equals the
directory name and a `description` that says *when* to use it — that
description is the only thing a client loads before activation, so it is what
makes the model reach for the skill. Keep the body under ~500 lines and move
detail into `references/`. Then run `build_plugin.py`, bump the minor version,
and add a test to `dev/tests/test_plugin.py` if the skill has structure worth
checking.

## Moving to a future Agent Plugins version

Schema identifiers are immutable, so a new specification release means new
canonical URLs. Vendor the new schemas next to the current ones in
`dev/schemas/`, update `AGENT_PLUGINS_VERSION` in `build_plugin.py`, and
change both `$schema` values together — a mismatch between `plugin.json` and
`mcp.json` invalidates the MCP half of the plugin while leaving the skills
loaded, which is a confusing way to fail.
